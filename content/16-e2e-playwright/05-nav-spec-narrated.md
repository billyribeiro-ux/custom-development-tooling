# Worked Example: E2E Test for This Site's Navigation

Let's read the course's complete E2E test suite: `tests/e2e/nav.spec.ts`. It verifies that the navigation the generator produces (Module 5.7) actually *works in a real browser* — Previous/Next buttons, arrow keys, progress indicators, and the disabled states at the start and end. It's a real, runnable safety net for the exact feature you've been using to read this course.

> [!DOGFOOD]
> This is the real spec that runs in the course's CI (Module 15.5). It tests the very Previous/Next buttons at the bottom of this page. Open `tests/e2e/nav.spec.ts` alongside this lesson, and run it with `make test`.

## Why these tests exist

The generator (Module 5.7) computes every Previous/Next link and progress number from the manifest. That logic is the heart of the site — if it breaks, *every* page's navigation breaks. These E2E tests are the safety net: they load the *actual generated HTML* in a *real browser* and confirm navigation works as a user would experience it. This is the E2E sweet spot (Module 16.1) — you genuinely can't verify "clicking Next changes the page" without a real browser.

## Test 1: the home page

```typescript title=nav.spec.ts
import { test, expect } from '@playwright/test';

test('home page lists the course and links to the first lesson', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveTitle(/Custom Development Tooling/);
  await expect(page.locator('h1')).toContainText('Custom Development Tooling');
  await expect(page.getByRole('link', { name: /Start the course/ })).toBeVisible();
});
```

Navigate to the home page (`/` resolves via `baseURL`, Module 16.3), then assert: the title matches, the `h1` shows the course name, and the "Start the course" link is visible. Three auto-retrying assertions (Module 16.4) confirming the index page (generated by `renderIndex`, Module 5.7) renders correctly. The `getByRole('link', ...)` is a semantic locator (Module 16.4).

## Test 2: the first lesson's disabled Previous

```typescript title=nav.spec.ts
test('the first lesson disables Previous and enables Next', async ({ page }) => {
  await page.goto('/lessons/001-welcome.html');
  await expect(page.locator('.progress-text')).toHaveText('Lesson 1 of 114');

  const prev = page.locator('.pager-prev');
  await expect(prev).toHaveAttribute('aria-disabled', 'true');

  const next = page.locator('.pager-next');
  await expect(next).toHaveAttribute('href', /002-/);
});
```

This verifies the *edge case* the generator handles (Module 5.7): the **first** lesson has no previous page. It asserts:

- The progress text reads `Lesson 1 of 114` — confirming the progress computation.
- `.pager-prev` has `aria-disabled="true"` — the generator disables Previous on lesson 1 (you saw this in the generated HTML way back in Phase 1).
- `.pager-next` links to a `002-` page — Next points to lesson 2.

Testing edge cases (first/last) is crucial — they're where off-by-one bugs hide (Module 1.5's "design the failure").

## Test 3: navigation actually moves

```typescript title=nav.spec.ts
test('Next and Previous buttons actually move between lessons', async ({ page }) => {
  await page.goto('/lessons/001-welcome.html');
  await page.locator('.pager-next').click();
  await expect(page.locator('.progress-text')).toHaveText('Lesson 2 of 114');

  await page.locator('.pager-prev').click();
  await expect(page.locator('.progress-text')).toHaveText('Lesson 1 of 114');
});
```

This is the core *behavioral* test (Module 16.4's navigate → act → assert): click Next, assert we're on lesson 2; click Previous, assert we're back on lesson 1. It proves the links don't just *exist* but actually *work* — a user clicking them moves between lessons. Auto-waiting (Module 16.2) handles the page loads after each click; no sleeps needed.

## Test 4: keyboard navigation

```typescript title=nav.spec.ts
test('arrow keys turn the page', async ({ page }) => {
  await page.goto('/lessons/001-welcome.html');
  await page.keyboard.press('ArrowRight');
  await expect(page.locator('.progress-text')).toHaveText('Lesson 2 of 114');
  await page.keyboard.press('ArrowLeft');
  await expect(page.locator('.progress-text')).toHaveText('Lesson 1 of 114');
});
```

This tests the keyboard navigation wired up in `app.js` (the arrow-key handler). Pressing ArrowRight should advance, ArrowLeft go back. It verifies *client-side JavaScript behavior* — something only a real browser running real JS can confirm (the E2E sweet spot again). Notice it tests a feature implemented in a *different* file (`app.js`) than the generator — E2E tests cover the *whole* system working together (Module 16.1).

## Test 5: code blocks render

```typescript title=nav.spec.ts
test('every lesson has working code blocks with a copy button', async ({ page }) => {
  await page.goto('/lessons/002-what-you-will-build.html');
  const firstBlock = page.locator('.monaco-block').first();
  await expect(firstBlock).toBeVisible();
  await expect(firstBlock.locator('.btn-copy')).toBeVisible();
});
```

This checks that the Monaco code blocks (the editors you've been using) render, with a Copy button present. It uses `.first()` to pick the first matching block and a *scoped* locator (`firstBlock.locator('.btn-copy')` — searching *within* that block). It confirms the generator's code-block output (Module 5.7's custom renderer) produces the expected structure.

## Test 6: the last lesson's disabled Next

```typescript title=nav.spec.ts
test('the last lesson disables Next', async ({ page }) => {
  await page.goto('/lessons/114-operating-model.html');
  await expect(page.locator('.pager-next')).toHaveAttribute('aria-disabled', 'true');
});
```

The mirror of Test 2: the **last** lesson (114) has no next page, so `.pager-next` is disabled. Together, Tests 2 and 6 verify *both* boundaries of the navigation — the first page can't go back, the last can't go forward. Boundary testing at both ends.

## What this suite demonstrates

Step back: in ~6 small tests, this spec verifies the *entire* navigation system end to end:

- The **home page** renders and links in (Test 1).
- **Both edge cases** — first page (Test 2) and last page (Test 6) — have correct disabled states.
- **Navigation works** via clicks (Test 3) *and* keyboard (Test 4) — covering both the generator's HTML *and* `app.js`'s behavior.
- The **code blocks** render with their controls (Test 5).

It's focused (a few critical journeys, per the pyramid, Module 16.1), uses semantic and scoped locators (Module 16.4), relies on auto-waiting (no sleeps, Module 16.2), and tests *real generated HTML in a real browser* — exactly what E2E is for. If a future change to the generator broke prev/next, *these tests would catch it before deploy* (Module 15.5). That's the safety net working.
